# Flood-response DT SoS simulator

This SimPy prototype compares resilience-profile strategies for a flood-response System of Systems (SoS). It models a drone, a pumping station, and a configurable fleet of equivalent boats assigned rescue or monitoring roles.

## Generated state machines

The Python state machines in `generated/` were autogenerated by itemis CREATE. **Do not edit these files manually.** The simulator raises events through the generated `hm` and `bm` interfaces and reads the resulting health and belonging states. Profile-specific health-to-belonging behavior remains defined by the generated machines.

## Project structure

- `main.py`: experiment runner, repeated simulations, aggregate and run-level outputs
- `config.py`: simulation parameters, profile configuration, fleet, thresholds, and mission assumptions
- `coordinator.py`: mixed-profile assignment, rescue-capacity management, profile-mediated join/leave requests, task dispatch, and resource-use measurement
- `cost_model.py`: activity-based cost quantities, allocations, and low/base/high estimates
- `digital_twin.py`: generated-machine adapter, state transitions, profile changes, telemetry, and commands
- `environment.py`: flood dynamics, victim arrivals, survival deadlines, expiry, pumping, and rescue
- `physical_units.py`: drone, boat, and pumping-station behavior
- `communication.py`: in-process publish/subscribe broker with latency and message loss
- `scenarios.py`: connectivity scenario and DT update loop
- `generated/`: itemis CREATE-generated profile state machines; preserve these files unchanged
- `requirements.md`: experiment requirements

## Install

Use Python 3.10 or newer:

```powershell
python -m pip install -r requirements.txt
```

## Run experiments

From this directory, run all three strategies with 30 repetitions each:

```powershell
python main.py
```

Run one strategy with all Poisson request-rate configurations, choose the number of repetitions per condition, and set a base random seed:

```powershell
python main.py --scenario mixed --profile-config all --runs 50 --seed 100
```

The default rescue sensitivity condition (`boat_emphasis`) uses a reduced pump-to-boat-area penalty (0.04) and increased boat capacity (3.0 victims per boat-step). Run the matched 2x2 sensitivity sweep across pump penalties 0.04/0.12 and boat capacities 2.0/3.0 with:

```powershell
python main.py --rescue-sensitivity all --runs 30
```

The four sensitivity identifiers are `reference`, `reduced_pump_effect`, `increased_boat_capacity`, and `boat_emphasis`. Output rows and aggregates distinguish these conditions.

Available strategies are `low_only`, `high_only`, and `mixed`. Profile configurations are `baseline`, `reduced_departure`, and `increased_departure`; these vary autonomous Poisson request rates. Profile membership policies independently govern which voluntary requests are accepted before an event is submitted through the generated belonging machine (`bm`). Health events enter through the generated health machine (`hm`), whose profile-specific rules determine any belonging effect. Use `--output-dir PATH` to choose a different output directory. Runs with the same repetition index use the same random seed across conditions.

In the Mixed strategy, the drone becomes Proactive at the first water threshold and remains Proactive. The pumping station progresses from Reactive to Proactive and then Controlled. Operational boats progress from Reactive to Proactive to Controlled; rescue boats become Adaptive at the final threshold. Reserve boats remain Reactive while waiting, adopt the current role-specific profile when activated, and return to Reactive when placed back in reserve. Threshold values are configured in `MIXED_PROFILE_THRESHOLDS` in `config.py`.

## Outputs

- `output/simulation_summary.json`: experiment parameters, aggregates by strategy/profile/rescue-sensitivity condition, run-level outcomes, state transitions, and coordinator events
- `output/simulation_runs.csv`: one row per run with mission outcomes and resource-use metrics
- `output/flood_history.csv`: time-series flood and victim data for every run

Mission success is an outcome: the run succeeds only if the configured victim-rescue target is met before survival deadlines. It is not determined by the assigned profile. Outputs include run-level outcomes, success rates, autonomous request outcomes, attached and Active DT-time, pumping-station active/service time and output, health-recovery readmission outcomes, activity quantities, and cost estimates by activity and category.

The cost pipeline uses activity-based costing adapted to this flood-response scenario. It maps data gathering, interaction, storage, processing, servitization, maintenance, and reserve-boat deployment to explicit activity drivers, then reports low/base/high estimates across IT infrastructure, resources, data activities, and investment. Repair cost grows with repair time; backup cost grows with deployed rescue time. Shared CapEx is amortized over the configured mission count; OpEx grows with mission duration. Rates in `config.py` are illustrative placeholder cost units, not market prices or values copied from the manufacturing study. Calibrate and source them before making monetary claims. DT-time remains a separate utilization metric.

The Poisson rates, membership policy, flood thresholds, boat throughput, victim survival time, success target, cost drivers, and cost rates are experiment assumptions in `config.py`; calibrate and justify them before reporting research results.

Active physical twins accumulate fault exposure while flood water is above the configured threshold. Every exposure interval advances their health by one state through the generated `hm` API. An unhealthy DT requests repair after it becomes non-Active; non-pump twins can be repaired while Passive or Prepared. The pumping station begins repair only in generated `Prepared` belonging; if it is Passive, the simulator requests `bm.leave_so_s` and starts repair only if the generated machine reaches Prepared. Repair restores the physical unit and raises `hm.recovery`. If the departure was health-related, the coordinator can request re-admission after repair through the profile membership policy and generated `bm` API, retrying at the configured interval. A Reactive pump that remains Active is not removed just to repair it. When expected rescue capacity is below the minimum required, the coordinator requests an eligible monitoring or reserve boat through the generated `bm` API. Voluntary SoS departures alone do not qualify for automatic health-recovery readmission. The generated machines remain authoritative for health-to-belonging behavior.

An Active DT still receives its assigned mission task as its physical twin degrades. Per-task success probabilities decrease linearly across health states: Ideal 100%, Defective 83.3%, Faulty 66.7%, Erroneous 50%, Malfunctioning 33.3%, Degraded 16.7%, and Failed 0%. Intermediate outcomes are sampled reproducibly per DT; physical unavailability still prevents execution. These are baseline assumptions, not measured reliability values. The pump's health communication channel is unavailable at Degraded or Failed until repair and recovery, but this reporting outage does not suppress the local task attempt or its health-based success probability. Task outcomes, pump communication downtime, repair requests/completions, backup requests/activations/deployment time, and successful pump service time are recorded in the outputs. Coordinator-driven health-recovery readmission runs only for High-only and Mixed strategies; Low-only does not initiate that recovery path. All health and belonging transitions continue to use the generated `hm` and `bm` APIs.
